# 桌宠互动与世界观：本轮实现和后续取舍

评估日期：2026-09-23。以 Nyalume-v2 当前源码为准；旧清单不等于当前接线状态。

后续落地：依赖与素材已从另一份工作区补齐，每模型配置、视角持久化与骨骼检查已实现。
配置方法、材料清单与验证范围见 [每模型配置与动作检查](model-profiles.md)。

## 本轮已落地

- 聊天输入改为三行起步、随内容增高的 textarea；Enter 发送，Shift+Enter 换行，输入法确认不发送。
- 共享回复渲染器支持 Markdown 表格，包括历史消息、流式回复、对齐、空格子和旧回复的行首 `\|`；代码块保留原样，窄窗口内横向滚动。
- 沿用已有 `@register` 注册表、执行分发、审计和权限闸门。没有另建桌宠控制框架，也没有修改全局输入钩子。
- 扩展 `pet_perform`，新增 `pet_configure`，补足状态白名单。`GET /api/pet/state` 供聊天状态侧栏按需读取；不启动桌宠、不增加后台轮询。
- 把原来未被引用的 `WORLD_VIEW_PROMPT` 接入 Nyalume 人设，标准助手不受影响。主动搭话也采用电脑世界观。记忆依据、低打扰和不惩罚离线写入提示词。

这些是可调用能力和表达规则，不是已经完成的长期剧情引擎。提示词也不保证每次模型表现完全一致。

## API 与工具机制

`tools.py` 的 `@register` 同时登记实现和参数，`tool_schemas()` 生成模型工具定义，`execute_tool()` 执行权限检查、调用和审计。

工具从 `~/.nyalume/pet3d_endpoint.json` 读取端口，只请求 `127.0.0.1`，超时为 2 秒；桌宠没启动时返回不可用。Agent 不接收任意 URL 或脚本参数。

| Agent 工具 | 桌宠端接口与字段 | 使用方式 |
|---|---|---|
| `pet_status` | `GET /pet_state` | 返回模型、动作库、模型列表、体力/心情、风格、手动/有效安静、搭话档位；丢弃 desktop、路径和媒体标题 |
| `pet_perform` | `POST /pet` | dance→name；idle；face→emotion；say→text；look→x/y |
| `pet_configure` | `POST /pet` | style→index；model→name；quiet→布尔 value；talk_mode→mode |

示例：`pet_perform(action="face", value="happy")`；`pet_perform(action="look", value="上")`；`pet_configure(action="quiet", value="true")`。

- 表情限定 happy/shy/surprise/angry/sad/sleepy/calm/love；视线限定左/右/上/下/前。
- 风格值为数字字符串 0–4；安静值为字符串 true/false；搭话档位为 quiet/reserved/normal/chatty/talkative。
- 模型切换仍通过原生重启机制，需要约 3–5 秒。先读可用模型列表。
- 服务端仍是单个 `_pending` 槽，多次连续指令可能覆盖。工具描述与 Agent 提示要求每次只发一个动作；响应明确写“已接收”，不冒充播放完成。本轮未引入动作队列。
- 日常模式继续保持纯聊天，工具定义与执行权限沿用既有约束。聊天侧栏的本地状态展示不等于给日常模式 LLM 工具权限。
- 调试接口 shot、原始骨骼控制、任意桌面操作没有注册成 Agent 工具。

## 参考与差异方向

[Weyrdlets 官方商店页](https://store.steampowered.com/app/2366060/Weyrdlets/)强调桌面宠物、陪伴、玩法与生产力结合；[Spirit City 官方商店页](https://store.steampowered.com/app/2113850/Spirit_City_Lofi_Sessions/)将精灵陪伴与待办、计时、习惯和日记结合。可以借鉴它们的低压力陪伴与环境一致性。

Nyalume 更值得发挥的是“能一起做事的居民”：用户的真实项目构成故事地点，经过确认的小约定构成支线，一起完成的事情构成共同记忆。区别点是任务与关系共享同一段生活经历；不宣称这一定是市场独有设计。

推荐先做一个可复玩的短闭环：

1. 用户明确说“这周一起把课程设计做完”。她提出一个小约定，由用户认可。
2. 沿用项目、任务状态和便签，记下事实性的目标与进度；无需观测用户屏幕。
3. 只有明确完成的事件才推进下一段，例如测试通过或用户确认答辩结束。运行状态 completed 只说明 Agent 回合结束，不能单凭它判定任务成功。
4. 自然收尾时出现一句短反馈；她之后能提起“我们上次修好的那个输入框”。
5. 保存一条可查看、可删的共同记忆。故事结局可因用户的选择不同，离线不扣分、未回应不自动算同意。

成长先表现为“记得偏好、延续约定、形成双方认可的昵称”，避免再建一套和日常模式好感度冲突的数值系统。不把体力低变成用户的照料负担；优先 sleepy 表情和自然待机，喘气/躲闪需要先验证模型动作适配。

## 现有 world 模块的实际缺口

当前 Web 启动会启动 `WorldManager`，但 Agent 没有读取 `get_prompt_context()`，对话没有接到 `record_chat()`，日记的保存/跨日归档/摘要生成尚未接成完整流程。原来的世界观常量也未加入 `persona_base_prompt()`；本轮已修复这一处。

不要直接把待播报模板全部注入上下文：模板中有未证实的天气、巡视描述，也有原始路径等数据；它们是台词，不能充当事件事实。下一步应先保存真实来源、时间和最小事实，再由事实生成可选文案，且复用桌宠的同一套安静/全屏/忽略预算。否则两套主动系统容易重复打扰。

日记应先做零额外模型调用的事件列表，修好跨日、重启恢复、去重与删除，再考虑用户主动要求的一次摘要。不要把“本地规则零 token”误当成把所有上下文塞入模型也零 token。

## Backlog 取舍

| 项目 | 可行性与价值 | 建议 |
|---|---|---|
| Agent 工具、状态回传 | 高；直接闭合聊天与角色反馈 | 本轮完成最小版 |
| 每模型配置 | 高价值，中等工作量；直接影响换模体验 | 已实现 scale/朝向/表情映射/动作白名单，菜单可打开配置 |
| 骨骼兼容检查 | 高；复用渲染器的 PMX/VMD 解析器 | 已实现脚本和两模型报告，区分缺失总数与非零位移/旋转轨道 |
| 缩放/旋转/当前模型持久化 | 高；成本较低 | 已实现按模型保存视角、每秒最多写一次；沿用现有当前模型记录 |
| 更多待机/互动动作 | 可行，素材适配成本高于代码 | 每个模型先验收少量动作；自然站姿保持兜底 |
| 演化行为/剧情 | 高价值；要先处理事实、冷却和存储 | 先一个真实任务闭环，复用表情和气泡，不重做骨骼叠加 |
| 媒体控制 | 中等；已有 SMTC 读取基础，控制支持取决于播放器 | 先用户明确请求的播放/暂停，之后再评估切歌 |

| 下载完成/每日首次启动 | 高；可以从自有事件产生 | 先接自有工具的完成事件与本地日期，不监视所有下载 |

| 运行期换模型 | 可做，但物理、资源释放和引用清理风险较高 | 先把现有重启切换做稳定；按实际换模频率决定 |

| 发布/更新 | 可行，有实际价值 | 先公开包白名单、构建验证和手动发布；自动更新独立设计 |

继续保留“不吞输入、不抢前台、不无条件置顶、分辨率优先”的约束。此次没有恢复被舍弃的姿势、截图监控、应用代操作或实时 LLM 骨骼控制。

## 需要的工具与材料

本轮无需新插件或外部服务。后续也能优先复用本地工具、便签、项目和提醒。

需要外部补充的主要是材料：有使用权限且骨骼兼容的动作、可测试的不同模型、歌词时间轴与来源。自动更新需要明确发布仓库/分发渠道；剧情正式扩展前需要用户认可一条试玩支线。

## 验证范围与环境限制

自动化覆盖真实聊天 HTML 的浏览器键盘/输入法事件、流式表格、历史表格、代码块和窄屏布局；工具通过临时回环 HTTP 服务验证注册分发、参数映射、错误、离线、日常模式和状态隐私白名单。

最初缺少的 `pet3d/node_modules`、`pet3d/motions/idle.vmd`、打包脚本和默认 2D 皮肤现已补齐。
两套真实模型已进行浏览器渲染、视角保存与重载验证；Windows 原生分层窗口、两进程换模交接和游戏内交互仍需人工验收。
