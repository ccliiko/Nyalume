# 3D 桌宠：想法与舍弃清单

> 记录"想过但没做"和"做了又砍掉"的东西，免得以后有人（包括我自己）把砍掉的又加回来。
> 最后更新：2026-09-21

## 一、已经做了（保留）

- 真 3D：three.js MMDLoader 加载 .pmx，逐像素透明 + 点击穿透（分层窗口 + 每帧 PNG）
- 输入：全局鼠标钩子 + 原始位移积分（游戏锁光标时用）；**钩子永不吞输入**
- 互动：左键按部位戳（头/脸/胸/手/裙/披风/腿）、拖拽（抓头发/衣袖/裙摆带动局部）、
  双击下一支舞、右键拖旋转、滚轮缩放、中键退出
- 表情：部位随机反应池 + 状态表情 + 主动表情接口（`face`）
- 视线跟随：以**她自己轮廓**为参照（眼睛在顶部往下 12%），眼球+脖子+头一起动
- 动作：动作库递归扫描、菜单逐个选、舞蹈收尾与自然站姿待机交叉淡出（`END_FADE`）
- 物理：ammo.wasm，头发/裙摆；收尾不再 reset 物理（避免裙摆瞬移）
- 视觉：三档光照 × 四档滤镜，组合成 5 档"风格"；滤镜走 2D canvas 原生调色
- 菜单：聊天窗口入口、二级页（动作 / 模型 / 配置目录），自动按最长标签算宽度、超窗口自动缩放
- 采集（L1，0 token）：前台窗口分类、全屏、空闲、总体 CPU、媒体（SMTC）、电量
- 本地状态：心情/体力/被戳/跳过几支舞（`~/.nyalume/pet3d_state.json`）
- 控制口：`POST /pet`（dance/say/face/look/style/model/quiet/talk_mode）+ `GET /pet_state`
- 主动搭话（需 `LLM_API_KEY`）：桌宠专属人格、打扰预算、被无视两次静默一小时、
  用户可选安静 / 寡言 / 正常 / 健谈 / 话痨；人格名称取当前模型目录名，
  提示词可包含媒体标题，触发条件包含持续活动 / 体力低 / 电量低 / 空闲
- 打包：公开版（1.2 MB，只带允许二配的 IRIS OUT）+ 自用版（38.7 MB）

## 二、有想法、还没做（backlog）

1. 更多待机/互动动作；**动作骨骼兼容性检查脚本**（报"这支舞用到但模型没有的骨骼"）
2. **把 `pet_*` 注册成 agent 工具**（`tools.py` 里一个装饰器），让 LLM 直接指挥她
3. **状态回传**：主 App 读 `/pet_state`（现在只有她读主 App 的 `/api/activity`）
4. **演化行为**：体力低会喘、被戳多了会躲、好感度阈值触发不同反应
5. **媒体控制**（播放/暂停/上一首/下一首）+ **歌词同步**（歌词来源要另找）
6. 更多触发条件：下载完成、剪贴板高峰期、"今天第一次开机"之类
7. **每模型一份配置**（scale/朝向/表情映射/动作白名单）——换模型最大的坑
8. **运行期换模型**（现在是"重启式"，3–5 秒）
9. 缩放/旋转/当前模型的持久化（现在只存风格、自动降帧、主动搭话档位、手动安静）
10. 双击开聊天窗；走路/跟随光标（聊天窗口已有右键菜单入口）
11. 发布流程（现在只打到 `dist/`，没做上传/更新检查）

## 三、明确舍弃（或者因技术不好实现暂时舍弃，之后或许会加回来）
### 姿势 / 动作
- **抱胸待机**：试用后姿态不自然，回滚；只保留自然站姿
- **手放裙子前面的站姿**：穿模，已回滚
- **趴姿待机**：试用后效果不理想，回滚
- **反应姿势层、捂头、双臂交叉比 ×**：手臂受模型披风/衣物遮挡，穿不过去；回滚骨骼叠加，只留表情和气泡反馈

### 物理 / 手感
- **加粗手臂碰撞体**、**让衣服刚性跟着身体**：更假
- **旋转时暂停物理**：治标
- **抓布料给物理刚体加真冲量**：只做了视觉偏移，真传导没做（还在 backlog）
- **拖拽超过一定距离的回弹**：其实是"帧率不够"的错觉，没做

### 交互玩法
- **戳空反应**（透明判定框）：不需要，砍
- **连击升级 / 抛出惯性 / 贴边偷看**：试过，一般
- **拍照模式**（自拍姿势、存到"人物/自拍"）：先去掉
- **桌宠里内置台词/聊天**（`interactions`）：有 bug 且 OOC，改成"主动搭话"
- **点她时吞掉这次点击**（游戏里不同时触发游戏动作）：会让系统面板点不动，
  而且钩子挡错输入会让整台电脑鼠标键盘失灵 → 永久撤销，钩子一律不吞
- **自动抢/还前台、每 2 秒无条件置顶**：会搅乱全屏游戏的输入/焦点 → 永久撤销

### 视觉
- **144 帧模式**（降分辨率换帧率）：用户明确否掉，分辨率优先
- **菜单里的"换光照""换滤镜"两项**：合并成"换风格"（数据还在，`window.__style(i)` 可手动调）
- **脸红**：只在表情池里闪过一帧，没做专门实现（暂时不管）

### 明确"不建议做"（评估后否掉）
- **视频小窗播放**（把别的窗口画面搬进她的帧里）：要 Windows.Graphics.Capture +
  每帧塞进现有 PNG 管线，DRM/独占全屏还会黑帧；Win11 自带画中画已覆盖
- **让她操作别的应用**（模拟点击/键盘）：风险高，且我们已经踩过输入钩子的坑
- **截图喂模型做视觉监控**：token 杀手（1–2k/张）+ 隐私
- **逐帧/每秒 LLM 驱动骨骼**：延迟与成本都不划算（应是"事件驱动 + 本地插值"）
- **用 LLM 直接生成整支舞蹈 VMD**：质量会崩，只适合程序化小动作（如自制待机）
- **把原始窗口标题/文件名发给云端模型**：窗口只发"类别"（剪辑/游戏/会议）；
  媒体标题会随主动搭话提示词发送，以便谈正在播放的内容

## 四、做不了 / 受限制（不是不想做）

- **胸部物理**：模型没有胸骨，躯干刚体全是静态
- **独占全屏盖不上去**：Windows 限制，游戏得用无边框窗口
- **游戏内互动必须先提权**：反作弊游戏是高完整性进程，UIPI 挡住低完整性的钩子
  （`启动桌宠-管理员.cmd`）
- **游戏内鼠标"移动"拦不住**：游戏直接读 raw input，拦不到
- **IRIS OUT 开头披风上抬**：模型绑定（披风挂在左腕）+ 动作本身，非代码问题
- **模型/动作的商用授权**：锁暝模型禁二配、两份动作禁商用 —— 要商业化必须换素材

## 五、2026-09-21 性能与手感这一轮

### 保留的改动（都带实测数字）

- **帧转换走 C 层**：`_png_to_bgra` 的预乘 + BGRA 换序交给 PIL
  （`convert("RGBa")` → `tobytes("raw","BGRA")`），6.6 → 4.1ms/帧；实测待机
  41.5 → 45.2fps、鼠标高频移动时 33.5 → 41.0fps。输出仍是"预乘 BGRA"，单测钉住。
- **视线换算搬出鼠标钩子**：钩子 / 原始输入那两个每秒上千次的回调只记位置，
  真正的换算放到页面 40ms 一次的 `poll_action`；视线值没变就不过桥；
  删掉右键旋转时每个事件写一行调试日志。
- **布料物理子步按状态走**：待机 1/120（抖动 40.9% → 20.2%），跳舞 1/70
  （同页面同支舞帧数 +18%）。跳舞时布料本来就在动，那点微抖看不出来。
- **眼神幅度收小 + 靠得近才跟**：眼睛 ±0.20 / ±0.17 rad（原 ±0.30 / ±0.26）；
  "靠近"改成按**她的轮廓**外扩自身尺寸 25%（原来是按窗口外扩 35%）——
  窗口比人大得多，光标离挺远她也一直盯着。
- **手指自然弯曲**：`tools/make_idle_vmd.py` 给四指三节 20° / 17° / 11°。
  轴和符号是从 IRIS OUT 等舞蹈里量出来的（左手指骨绕本地 **-Z**、右手 **+Z**，
  舞里的握拳到 80~110°）。拇指不弯：它的轴是 X/Y/Z 混的斜轴，小角度不值得单写。
- **菜单/气泡永远在 UI 顶层**：sprite 加 `renderOrder = 999`。光有
  `depthTest:false` 不够——透明物体之间仍按 z 从远到近排，墨镜这种半透明材质
 比菜单近就会后画、把菜单盖住（火花、洛茜实测）。
- **默认风格改成"游戏味·浓郁"（索引 2）**：`柔和`那档环境光 0.6、轮廓光 0，
  加法光多、没有边光，所有模型都会平一档灰一档（锁瞑也一样）。Python 侧
  `cfg.get("style", 2)`、页面 URL 兜底也改成 2。
- **材质归一（只统计有贴图的材质）**：加载后按整套平均把 `color`/`emissive`
  拉回常用档（`diffuse 1.00` / `emissive 0.100`），材质之间相对明暗不变，
  偏 <12% 不动。基准**只统计有贴图的材质**——three 只对这类做
  `emissive *= 0.2`，没贴图的保留原 ambient，混在一起算会偏；全都没贴图才退回全部。
- **垃圾物理数据兜底**：质量 > 1e4 的刚体一律改成"跟随骨骼"的静态体
  （希希芙尾巴 2.5e11 → 8 秒不再沉 6.99；菲比 8 根带子 1.7e6 同理）。
- **主模型挑选规则**：目录里混着武器/道具时不再按名字排序取第一个
  （那会让桌宠加载一根"手杖（整.pmx"，看着就像窗口不见了）。规则：先踢道具
  （武器/手杖/道具/锤子/手机/喇叭/泡泡/葡萄/书/杖），再挑名字含角色名的；
  角色名从目录名推（去 `_by_` 与【】前缀，取"—"后、"·"前那段）；
  同名多个取排序第一个（火花那两个 → （修2））。`启动桌宠3D-管理员.cmd`
  的目标已指向火花（修2）。
- **显示窗口被系统收走就重建**：`_reassert` 里先 `IsWindow` 判断，窗口没了就
  重建 + 重新置顶 + 重注册原始鼠标输入。缩放窗口/切全屏之后窗口被系统销毁时，
  以前会变成一个"看不见但一直在跑"的进程，只能去任务管理器结束。
- **调试探针**（页面内，`viewer.html`）：`__probeJitter`（布料抖动 / 是否一直下沉）、
  `__probeLook`（渲染后画面的饱和度 / 亮度 / 对比度）、`matPeek`（材质均值）。
  用法：`viewer.html?...&probe=6000` 或 `&look=3500`，结果写进页面标题。
- **本轮试验中的互动/手感**：摸头时表情停留约 1 秒、短暂看向正面并轻点头，
  手臂保持自然待机；眼神、拖拽、旋转的平滑改按实际帧时长计算。
  `GET /pet_state` 增加显示帧率和帧间隔 p95，便于比较不同模型与动作。
  这几项仍需实机观感验证。
- **菜单命中与显示同坐标**：菜单 Sprite 位于相机前方，点击区域按该深度的
  透视比例计算，避免模型页、风格页点到上方一项。野餐式 MikuQ 的模型尺寸较小，
  旧算法中菜单平面与模型中心的投影比例差约 12%，足以偏出一行；洛茜约 2%。
- **送帧限两帧在途、窗口在消息线程恢复**：用户报告视频式顿挫与窗口消失；
  日志显示送帧积压和窗口连续重建。单帧限流实测约 30fps，现最多允许两帧在途，
  Python 端贴帧忙时丢掉重叠帧；恢复窗口交给原消息线程。待重启后实机验证。
- **撤掉逐进程 CPU 排行采集**：Windows 上 `psutil.process_iter(["name", "cpu_percent"])`
  每次耗时约 1.3–2.2 秒，采集周期与周期性停帧吻合；总体 CPU 数值保留。
  重启后连续日志中不再出现每隔几秒一次的 1–2 秒停帧。

### 这一轮试过并舍弃

- **降分辨率换帧率**：Python 侧放大比省下的解码更贵（7.5 → 11.4ms/帧）
- **帧改用 WebP**：Chromium 里编码 23.6ms，比 PNG 慢 3 倍
- **把 GIL 切换间隔调到 1ms**：无变化
- **`preserveDrawingBuffer: false`**：41.9 vs 41.5fps，无意义
- **复用 DIB / DC**（省掉每帧 CreateDIBSection）：只省 0.25ms/帧
- **物理求解迭代 10 → 25**：抖动 40.9 → 39.9%，帧数还掉；**加阻尼**：无变化
- **看门狗**（推帧停 20 秒就自己退出）：用户否掉——"这种情况让代码判断感觉不太好"
- **拇指弯曲**：轴太斜，小角度不值得
- **在全局鼠标钩子里做视线换算**：每秒上千次回调抢 GIL，越算越卡
- **单帧传输限流实验**：同机锁瞑待机约 49fps，洛茜重启后约 30fps；
  当前改用最多两帧在途，关注帧间隔和观感。

> "灰蒙蒙 / 塑料感"、"跳舞卡顿"这些还没定论的判断，另开一份
> `docs/pet3d-待验证猜测.md`，别混进这份清单。

## 六、2026-09-22 "每隔一段时间掉一下 + 主动搭话从不触发"（同一个根因）

**根因：`ctypes.windll` 是进程级单例，而 `python -m pet3d_win` 会把模块加载两份。**
`proactive._log` 里那句 `from .pet3d_win import _log` 就是触发第二份的开关：
第二份在自己的模块代码里重设了共享的 `UpdateLayeredWindow.argtypes`，把第 8 个
参数换成**它自己的** `_BlendFunction` 类。之后主实例每帧贴图都是
`ArgumentError: expected LP__BlendFunction instance instead of pointer to _BlendFunction`
（实测 63 条/秒全失败）→ 推帧停 20 秒 → 自动重启，**80 秒一个循环**。

- 复现只要 6 行：先 `import_module("...pet3d_win")`，再把同一个文件当 `__main__`
  exec 一遍，然后调 `UpdateLayeredWindow` → `ArgumentError`。
- 和之前那个 60 秒必崩的 `GetMessageW` 是**同一类**坑（当时只按函数打了补丁，
  所以换个函数又冒出来）。
- 主动搭话"一次都没触发"也是它：`talkative` 间隔 3–8 分钟，进程每 80 秒重启一次，
  `next_allowed_at` 永远等不到。（另外当时 23:00–08:00 还有深夜档，本来也不开口。）

改了三处：`proactive._log` 直接写日志文件、不再 import `pet3d_win`（去掉第二份模块）；
`UpdateLayeredWindow` 第 8 个参数写 `c_void_p`（跟 `GetMessageW` 一样不写死结构体）；
`tests/test_pet3d.py` 加一条回归（断言 `proactive._log` 不会往 `sys.modules` 里
新增 `pet3d_win`）。32 个测试通过。

**修后取样 15 分钟**（01:52:20–02:07:20，同一进程 PID 31416 没重启）：
`呈递失败=0`、`推帧停了=0`、`重启=0`；推帧稳定 604–626 帧/10 秒
（约 61fps，未回音 ≤2）；`主动搭话：先不说（…）` 正常按原因记录两条。
进程树内存 ~1.6GB / WebView ~2.35GB 但 15 分钟内是平的（不是泄漏，但偏大，待查）。

**删掉深夜档**（用户定稿：她本来就没声音，半夜搭一句话更像陪着）。
先按 `NYALUME_PET3D_NO_QUIET_HOURS=1` 临时放行验证过一次（02:17:32）：
`propose[陪伴] → say '夜深了还在学习呢，要不要歇会儿？'（194 token）`；
同一晚 Blender 全屏时正确记了 `先不说（全屏（游戏/视频））`。确认好用之后
`QUIET_HOURS` 和那个环境变量一起删了——深夜不再挡，"人不在（空闲 >15 分钟）"
那闸仍然有效，所以半夜没人在电脑前她也不会自说自话。

### 台词气泡：无框 + 按字数决定停留（2026-09-22）

- `kind === "say"` 的台词改成**无框**（白描边 + `#e0559a` 填充），像符号那样
  压在桌面/头发上都看得清，但不带白底圆角框。
- 停留时间 `bubbleSecs()`：**≤10 字 5 秒，之后每多 5 字 +1 秒**
  （11–15 字 6 秒，16–20 字 7 秒…，40 字台词 11 秒）。
- 无框 ≠ 会飘：`showBubble` 新加 `drift` 参数，只有符号（♥ ♪ zzz）飘着淡出，
  台词原地**满不透明度**撑到时间结束——不然长台词一边飘一边淡，还没读完就没了。
- 实测（截图逐像素比对，同一时刻 t=5.6 秒）：3 字短句的白描边像素已回落到底噪
  （150 → 105），17 字长句**还在**（352 → 350），7.6 秒才消失；差异图上旧有框版本
  是一整块实心白矩形，新台词只有文字笔画。
- 摸头反应的台词（`showBubble(text)`，第 741 行附近）**仍然带框**，没动。

### 换模型根本没生效 + "关掉 Codex 她就掉"（2026-09-22 凌晨）

- **换模型/换动作目录/选文件夹全都静默失败**，根因是 `_NativeApi.restart_with` 里
  那个闭包 `put()` 写了 `argv += [flag, value]`——`+=` 是赋值，`argv` 于是变成
  `put` 的局部变量，上一行 `if flag in argv` 直接 `UnboundLocalError`。
  异常被 pywebview 吞掉，pythonw 又没控制台，表现就是"右键点模型没反应"。

  `return True`。回归测试：`test_restart_with_rewrites_model_flag`（断言重写

### 为什么模型"发灰"——環境色被当常量加白（2026-09-22 凌晨，已修）

用户对照 Blender：同一只模型 Blender 正常、桌宠发灰。用 `%TEMP%\nyalume_pet3d_frame.png`
（第 200 帧的 RGBA 原图，透明背景，无桌面干扰）逐像素统计，找到了硬数字：

| 锁瞑 | 平均饱和度 | 有色像素(sat>0.25) | 平均亮度 |
|---|---|---|---|
| 贴图本身（15 张按像素加权） | 0.366 | 52% | 0.384 |
| 桌宠渲染（柔和·浓郁） | 0.098 | 12% | 0.584 |
| 原版·无滤镜 | 0.124 | 17% | 0.525 |
| 原版·无滤镜 + 把 emissive 清零（下限参考） | 0.255 | 32% | 0.364 |

**根因**：MMD 的"環境色"(ambient) 在 MMD 里是**乘纹理**再加的；three 的 MMDLoader 把它
塞进 `material.emissive`，也就是**当常量加白**（有贴图的材质还乘 0.2 想让别过亮）。
常量加白会同时提亮和掉饱和——深色的头发/衣服被抬成灰粉。我们那套"归一"里还有
`aK = 0.1 / aAvg`：模型 ambient 通常 0.5(sRGB) → 乘 0.2 → 0.043，于是 aK≈2.3，
**等于把加白又放大一倍多**。这就是"锁瞑也变灰了"的来源。

**改法**（两处、共 6 行）：有贴图的材质改成 `emissiveMap = map` 并 `emissive *= 5`
（抵掉加载器那个 0.2），等效于 MMD 的 `tex * ambient`；同时删掉归一的 `aK`
（只保留 diffuse 的 `dK`）。

**改后实测**：锁瞑 柔和·浓郁 sat **0.416** / 有色 57% / 亮度 0.341（亮度回到贴图
自己的 0.384 附近）；洛茜 柔和·浓郁 sat 0.333 / 有色 48% / 过曝只有 1.4%。
同一改动对贴图本身没动过任何像素，纯粹是不再拿白色往上糊。

|---|---|---|

### 脚部 IK 按动作自动决定 + 动作切换改硬切（2026-09-22）

**"有些动作腿卡住、弯不下来、脚像钉在地上"的真凶是脚部 IK**（用户自己猜对了）：

- 运行时骨骼值，同一支「今晚战个痛快？/女.vmd」同一时刻：
  脚部 IK **开** → `左ひざ=0.004,0,0,1.000`（完全直、锁死）；**关** → `左ひざ=0.795,0.153,-0.172,0.561`
  （屈膝 111°，正是动作数据里的值）。物理开/关完全一样，所以跟物理无关。
- 机理：MMD 的「左足ＩＫ/右足ＩＫ」是目标点，动作没给它写帧时目标停在静置位，
  解算器为了把脚踝拉到那个点就把膝盖掰住。这类动作（没写 IK 轨的）很常见。
- 排错时踩的坑：一开始查 `objects.ik` 判"没建解算器"，其实叫 `objects.ikSolver`
  —— 结论被带偏了一轮，**教训：以后先看 three 源码里字段名再下判断**。

改动两处（都在 `viewer.html`）：

1. `applyIK(clip)`：`helper.enable('ik', useIK && 这支动作有没有 IK 轨)`。
   加载和每次换动作都走它；菜单里的"脚部 IK"仍然是总开关（关了就永远不开）。
2. 换动作不再跨淡入跨出（`crossFadeTo` → `from.stop()`）：MMD/Blender 播放动作本来就是硬切，
   0.9 秒的过渡里会出现"半待机半动作"的中间姿势（坐姿的舞就是在这段穿模）。
   切完照旧 `settlePhysics()` 让刚体重新贴合骨骼，结束时的收尾淡出保留。

另外修了一个会**悄悄改配置**的坑：`_remember_dirs` 原来把"这次 vmd 所在目录"整体记成
动作库，直接用文件启动一次就会把用户的动作库设置换成那个文件夹（我调试时被坑过一次）。
现在只在"给的是目录"时才记。

### 切动作残留姿势（"跪下 + 低头"）修掉（2026-09-22）

- 现象：跳「女」（坐姿）时点一下/或让它自然播完回待机，她就**跪着+低着头**卡住；
  换别的舞要等那支舞自己写到那些骨头才恢复。
- 根因：`MMDAnimationHelper` 每帧是 `_restoreBones()`（从**上一帧的快照**）+ mixer 覆盖，
  新动作没写到的骨头会**原样留着上一条动画的姿势**。待机这支动作没写腿/腰/头，
  所以坐姿的最后一帧就留在身上了。上一轮把过渡改成硬切后更明显（以前跨淡入还能糊掉一部分）。
- 改法：`resetToRestPose()` —— 切动作前（以及舞跳完开始收尾淡出时）先
  `model.skeleton.pose()` 把骨架按 `boneInverses` 回静置，再调 `helper._saveBones(model)`
  把助手那份快照一起刷新，新动作没覆盖的骨头就回站姿。
- 实测（用新加的 `POST /pet {"action":"shot"}` 落盘 RGBA 原图量轮廓，洛可可）：

| 原图轮廓 | 高 | 宽 | 脚底 y |
|---|---|---|---|
| 待机 | 402 | 165 | 511 |
| 跳「女」第 4 秒（坐姿） | 365 | 201 | 474（矮、宽、脚离地） |
| 舞播完自然收尾后 | 403 | 166 | 511（= 待机） |
| 舞中手动切回待机后 | 402 | 166 | 510（= 待机） |

- 顺带：单击实测**不会**切回待机（日志 `tap leg`、`motion` 仍是「女」）—— 之前看到的
  "回到待机"是这支舞本身只有 ~10 秒。
- 新调试口：`POST /pet {"action":"shot"}` 把当前帧原图存到
  `%TEMP%\nyalume_pet3d_frame.png`（`_last_png` 现在无条件保留最新一帧的引用，不再依赖 DEBUG 环境变量）。

### 显示架构重构：窗口固定全屏 + 只贴她那一块（2026-09-22 凌晨）

之前的问题：缩放靠"把窗口变大"，窗口顶到系统极限后相机再推，她就比窗口还高，
**同时被窗口上下边切掉头和脚**（窗口不在屏幕正中时就露出两刀硬边）。

**新架构**（用户提的思路，我来实现）：

- 可见的分层窗口**固定铺满工作区**（`0,0 1920x1032`），**永不改尺寸/位置**；
- 页面只渲染"她那一块"画布：`baseW*zoom × baseH*zoom`（`baseW/baseH` 由 Python 用
  `?box=WxH` 传进来 = 启动时的 `--size`）。画布跟窗口尺寸彻底解耦；
- Python 维护一张**常驻的全屏 DIB**：每帧先清掉上一帧占的矩形，再把她那块贴到
  `(_x,_y)`（只拷与窗口相交的部分），最后整块 `UpdateLayeredWindow` 提交；
- 缩放 = 只改那块画布 + 用同一个锚点重算 `(_x,_y)`；拖拽 = 只改 `(_x,_y)`。
  超出屏幕的部分自然被屏幕边缘挡住 —— 所以相机放到 3 倍也不会在桌面中间出现硬边。

**实测**（同一台机器，1920x1080）：

| 状态 | 画布 | 图层窗口 | fps |
|---|---|---|---|
| 1× | 440×660 | `0,0 1920x1032` | 62.4 |
| ~2.5× | 1108×1662 | `0,0 1920x1032` | 35 |
| 3×（上限） | 1320×1980 | `0,0 1920x1032` | 27.4 |

3× 时她高 1271px、上下边距 360/349 —— **完整画在自己画布里**，不会被切。
交互也都实测过：单击 `tap belly ✓`、菜单 `menu choose quiet ✓`（坐标映射没坏）、
用户自己拖动 `drag end moved=460 ✓`。

**代价**：帧的搬运量 = 她的显示像素（这条 CPU 管线按像素收费），所以 3× 时 2.6M 像素
→ 27fps；1× 还是 62fps。想"铺满屏幕还保持 60fps"只能走原生/GPU 直出（另一件事）。

顺手修的两个 bug：
1. `request_resize` 的早退条件原来拿"最近一帧的尺寸"比 —— 画布是页面立刻改的，
   帧晚一两帧才到，于是永远相等 → **缩放定位从来没执行**（她不会跟着光标锚定）。
   改成跟"上次请求的尺寸"比。
2. 页面把 `baseW` 用在定义之前（TDZ ReferenceError），整页脚本不跑、一帧都不出。

#### 补：放大时她往右下漂的 bug（同一天）

现象：滚轮放大时她不跟着光标锚定，反而一路漂向屏幕右下角。

根因是**锚点归一化的分母用错了**：滚轮那一刻记的是"光标相对她画布的像素偏移"，
但等到 `request_resize`（页面还 debounce 了 140ms）再除以"当前帧宽度"时，
画布已经**先一步变成新尺寸**了 —— 分子的偏移是旧画布量的、分母是新画布，一乘
刚好把偏移还原成原值，于是 `_x = 光标x - 原偏移` 恒等于老位置，位置永远不更新；
而她是被画布**居中**画的，画布一大，视觉上就往右下跑。

改法：在**滚轮那一刻**就把锚点算完整（屏幕坐标 + 归一化位置 `ux/uy`）存进 `_zoom_at`，
`request_resize` 直接用，不再依赖"当前帧是哪块画布"。同时把等帧定位的条件从
"尺寸变了"改成"等到目标尺寸的帧"（画布先变、帧后到，旧的 `from` 比较会永远成立或
永远不成立）。实测：画布 440×660 → 647×970，位置 1456,348 → 1351,255，
期望（光标底下那点不动）1352,255 ✓。

#### 补二：缩放时"先漂一下再弹回去"（同一天）

上一版把定位放在"目标尺寸的帧到了才做"，于是**尺寸先变、位置后变** —— 中间那几帧
尺寸是新的、位置还是旧的，看起来就是先漂一下再弹回光标锚点。用户要的是"光标永远
停在同一个点上（比如左眼）"。

改法：把整套 `_pending_resize/want` 机制删掉，改成**逐帧按锚点摆**——
锚点在滚轮那一刻就存好（`_zoom_at` = 光标屏幕坐标 + 归一化位置），
`_present_frame` 里只要这一帧的尺寸和上次摆位时不同，就用它重算 `_x/_y`
（`x = 光标x - ux*画布宽`）。每一帧都锚，所以不存在"漂一下"。

实测（光标放在她左眼位置，逐格滚）：
放大 6 格，画布 440×660 → 698×1047，光标在她画布里的相对位置恒定 **(0.420, 0.220)**；
缩小 5 格，698×1047 → 475×713，相对位置同样 **(0.421, 0.219)**。

#### 补三：缩放闪一下（同一天）

现象：缩放时模型闪一下（整只消失一帧）。

日志抓到的证据：每改一次画布尺寸就出现一次 `frame blank #N` → `frame has pixels #N+1`，
一格一刀，正好对上。原因是 `renderer.setSize()` 会重建 WebGL 缓冲区（内容清空），
而抓帧是 60fps 的独立定时器，赶在下一帧渲染之前抓到的就是这块空缓冲区 → 推给 Python
就是一张全透明帧 → 她闪一下。

改法（页面上 3 行）：`applyBox()` 里置 `boxDirty = true`，`pushFrame()` 见到它就跳过，
`tickFrame()` 里 `renderer.render()` 之后清掉 —— 即"等新尺寸真的画出来再推帧"。

实测：连续放大 8 格 + 缩小 6 格，**空帧切换 0 次**（改之前是每格一次），
并且光标锚点依旧钉住（相对位置恒为 0.450,0.300）。

### 试了"让 WebView2 自己透明"（GPU 直出）—— 卡在透明合成（2026-09-22）

用户点名试这条路：WebView2 窗口自己当桌宠显示（置顶 + 点击穿透 + 不推帧）。
做了个 `NYALUME_PET3D_NATIVE=1` 的**实验分支**跑起来量了：

**好消息：CPU 差 10 倍。** 同一只模型、同一块 440×660：

| 路径 | CPU（12 秒窗口） |
|---|---|
| 老路径（分层窗口 + 每帧 PNG → 桥 → Python 解码 → ULW） | **56.7%** 单核 |
| native（WebView2 自己显示，像素不过 Python） | **5.2%** 单核 |

**坏消息：透明合成不干净 —— 这条路直接走不通。** 用日志里那个 HWND 做"显示/隐藏"对照：

| 状态 | 她那一块四角的像素 |
|---|---|
| 窗口**显示** | (240,240,240) × 4 —— 一片均匀灰 |
| 窗口**隐藏** | (216,185,188) / (125,121,142) / (215,202,221) / (123,116,138) —— 真实桌面 |

两张图 **99.9% 像素不同**：窗口把她那一整块桌面盖住了。`240,240,240` 是 WinForms 宿主的
默认底色（页面 body 本来就是 `transparent`，所以灰不是页面画的）——
**pywebview 的 `transparent=True` 在 Windows/WinForms 上做不出逐像素透明的窗口**，
这正是当年绕开、改用分层窗口 + 每帧 PNG 的原因。

顺带修了一个真 bug：Python 启动会发一条 `{"kind":"fps"}`，页面的 fps 分支**无条件**重挂推帧
定时器，绕过了"native 不推帧"——结果 native 模式下页面照样推帧、Python 又没有显示线程，
于是"显示线程不在了 → 自动重启"反复重启。现在这个分支也尊重推帧开关了（对老路径无影响）。

**结论**：native 直出要能用，得换掉 pywebview 的宿主（WPF 的 AllowsTransparency，或者
直接 WebView2 + DirectComposition 自己做宿主）——那是窗口层重写，不是改几行。
实验分支已删掉，只留下上面这个 fps 修复。

### 修：视线跟随左右（还有上下）方向是反的（2026-09-22）

用户反馈："光标在她左边（左眼位置）她还是往右看"。

**先用像素量了一遍**（把光标放她脸的左/右，看刘海+瞳孔那团暗部的质心往哪边移）：
- 改之前：光标往右 → 暗部质心 **左**移 7.3px（身体整体也在动，所以再用"暗部质心 − 身体质心"归一化：+2.6px 同向）→ **反了**；
- 上下：光标往下 → 质心 **上**移 3.2px → 也反了。

**原因**：这套骨架（頭/首/左目/右目）的**骨骼局部轴和世界轴反着**（等效绕 Z 转了 180°：
本地 X = −世界X、本地 Y = −世界Y），所以 `rotateY/rotateX` 的正负都跟直觉相反。

改法：在输入那一步统一翻符号（`lookTx/lookTy` 各加一个负号），只改一行、不动幅度和
平滑逻辑：

```js
lookTx = THREE.MathUtils.clamp(-action.x * 1.1, -0.20, 0.20);
lookTy = THREE.MathUtils.clamp(-action.y * 1.0, -0.17, 0.17);
```

**改后实测**（三次取样、用"暗部质心 − 身体质心"消掉待机晃动，σ≈0.5px）：
- 水平 R−L = **+5.39px**（光标往右她也往右 ✓）
- 垂直 D−U = +1.09px（同向 ✓，上下幅度本来就小，噪声也大，属于"至少不再反向"）

#### 补：视线符号 —— 头和眼睛要**相反**（同一天，第二次修正）

第一次我只把输入 `lookTx/lookTy` 统一翻了个符号：头/脖子正了，但眼睛**反而**反了
（用户："现在彻底反了"）。两次反馈合起来说明：这套骨架里**眼球那一对的轴向和头/脖子相反**。

现在的做法：
- 输入照旧统一取反（`-action.x`, `-action.y`）→ 头/脖子按 `+lookX/+lookY` 转（正确方向）；
- 眼球改成 `eye.rotateY(-lookX)` / `eye.rotateX(-lookY)`（单独再翻一次）。

只改了这一处（眼球那两行）。像素测量能确认头部方向（暗部质心随光标同向移动、
"暗部质心 − 身体质心"归一化后 R−L = +5.4px）；但瞳孔太小、和刘海混在一起，
自动化量不出眼球，这一条的最终判据是用户的眼睛。

#### 补二：视线符号的最终结论（同一天，第三次）

用"头和眼球的**朝前向量**世界 x 分量"当客观判据（`+x = 画面右`，这个锚点由用户反馈验证：
翻转后头的前向指向画面右、而光标在画面左，用户说"头不对"）：

- 每个骨骼的旋转值符号 = 它朝前向量的符号（实测头、眼球都如此）；
- 正确映射：光标在画面右（`action.x > 0`）→ 旋转为正 → 朝前向量为正 → 她看向画面右 ✓；
- 所以 **`lookTx = +action.x`、头/颈/眼球都用 `+lookX`** 就是对的 —— 也就是**最初的代码**。

结论：这一轮我先后"统一取反"和"只翻眼球"两次都是错的，属地把**对的东西改坏了**。
现在两处都已还原成最初逻辑，并用 lookdiag 数据核对过（temp 诊断已删）。
教训：这种"看着反了"的问题，先用**客观量**（骨骼朝前向量、而不是我猜的像素质心）定方向再动手；
像素质心那套测的是刘海/头的整体位移，方向会看反。
